# Brief: red-receipt

**Date:** 2026-10-28
**Tier:** 3 - a new cycle.sh verb and a close-story gate, worker and planner prompts, the story template, /vulyk-plan, tests, an ADR

## Request (verbatim)

> Истинный TDD-контракт («Red-to-Green Receipt») для критичных историй
> Как сейчас в «Вулике»: В /vulyk-plan есть отличное правило: история с ветвлением, парсером, деньгами или безопасностью должна называть один тест, который упадёт при поломке логики (verify-gap). А в worker-test / worker-code тест и код часто пишутся в одной волне или проверяются уже в зелёном состоянии.
>
> Что делает команда Claude Code внутри Anthropic: В их внутреннем гайде ключевой паттерн — Strict Agentic TDD. Модели запрещено писать имплементацию, пока на диске не зафиксирован падающий тест (именно по нужной причине, а не из-за синтаксиса), и при этом категорически запрещены моки для ещё не написанной логики.
>
> Как внедрить в «Вулик» без лишних агентов:
>
> Не нужно гонять отдельного агента! Достаточно добавить в cycle.sh микро-глагол или флаг cycle.sh verify-red <story-file> (или проверять это в close-story по истории git/штампу для багфиксов):
>
> Воркер пишет тест на баг/фичу.
>
> Запускает cycle.sh stamp-red <story-file> — скрипт за 1 секунду и 0 токенов убеждается, что команда из ## Verification реально падает (exit != 0), и пишет однострочный штамп red_verified_at: <hash/ts>.
>
> Воркер пишет код, тест зеленеет, close-story видит штамп red_verified_at и закрывает историю.
>
> Профит: Абсолютная гарантия (за 0 токенов!), что тест реально тестирует новую логику, а не является пустышкой (tautological test), которую verify-gap на статике не всегда может распознать.

## Answers

1. Охват - Критичным, тест в той же истории (Рекомендую): Планировщик ставит в истории метку по тому же списку, что уже есть в vulyk-plan.md:78: ветвление, парсер, деньги, безопасность, запись данных. Тест пишется в той же истории до кода. Путь «тест-история в поздней волне» для таких историй закрывается. Остальные истории живут как сейчас: ремонт тех, где штамп не нужен, ничего не стоит.
2. Багфиксы - Наследует метку (Рекомендую): Если среди историй, которые чинит ремонт, есть критичная, история ремонта получает ту же метку. Тогда воркер сначала воспроизводит баг падающим тестом, штампует красный и только потом чинит. Именно так ловится «театр тестов»: совет уже дважды видел зелёные тесты на сломанном коде (anomaly-telemetry, раунд 1).
3. (horizon H1) Причина - Добавить (Рекомендую): В истории пишется ожидаемый текст падения. stamp-red принимает красный, только если этот текст есть в выводе, и не принимает сбой запуска. В квитанцию идут хеш теста, команда и хвост вывода для ревьюера. close-story отказывает, если квитанции нет или тест правили после неё. Цена: одно поле в истории, а правка теста после штампа требует перештамповки. - adopted
4. (horizon H2) Авто-красный - Не добавлять (Рекомендую): Во временной копии нет node_modules, .venv и прочих неотслеживаемых зависимостей ульев. Там тест упадёт не по той причине и сойдёт за красный. К тому же критичные истории проверялись бы вдвое дольше в пределах тех же 540 секунд. Штамп воркера с квитанцией просто идёт в живом дереве. - declined
5. Требования - Всё верно, покажи план (Рекомендую): Семь пунктов идут в ## Asks. Я пишу план и останавливаюсь на твоё одобрение.

Side-agent note received mid-grill (model text, not an owner quote): a bare red stamp does not know why the command failed; a worker can break code for a minute to get the stamp; a test story after the code can never be red. Covered by answers 1 and 3; the "break the code for a minute" path is a named residual bypass, not closed by a script.

## Asks

1. `cycle.sh stamp-red <story-file>` за секунду и 0 токенов убеждается, что команда из ## Verification реально падает, и пишет однострочный штамп red_verified_at.
2. Порядок работы: тест → stamp-red → код → зелёный. close-story закрывает критичную историю, только если видит штамп.
3. Воркерам запрещено писать реализацию до падающего теста и запрещены моки для ещё не написанной логики.
4. Без новых агентов.
5. Критичную историю помечает планировщик по текущему списку. Тест лежит в той же истории, путь «тест после кода» для неё закрыт.
6. История ремонта наследует метку критичной истории, которую чинит.
7. (horizon) stamp-red принимает красный только с ожидаемым текстом падения и пишет квитанцию с хешем теста. close-story отказывает без квитанции или если тест правили после неё.
