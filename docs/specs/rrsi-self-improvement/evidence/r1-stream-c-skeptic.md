## 1. Хайп против кода

**Что показывает пост.** Пост t.me/startup_14day/1080 («Агент, который сам улучшает свои навыки», 294 просмотра на 2026-09-29) несёт одну цифру: Terminal-Bench 2.1 74.2 → 80.2. Это **in-sample** число: для coding «Evolve set: all 89 Terminal-Bench 2.1 tasks» (`domains/coding/README.md:3`, `domains/coding/rrsi.json` `_doc`). Отложенной выборки из TB нет. К тому же число снято **в момент отбора**. Счёт нового incumbent — это оценка самого победителя (`rrsi/loop.py:326-335`: `new_S = winner.ev.S`, `S_star = max(...)`), повторного замера нет. Это классическое проклятие победителя: argmax по 2 кандидатам × 20 раундов на шумной оценке. По статье evolve-числа тоже selection-time («measured in the same window», arxiv.org/html/2609.24972v2, прочитано 2026-09-29). И «сам улучшает навыки» — неверная рамка. Это офлайн-поиск по фиксированному бенчмарку с замороженной моделью, а не обучение на работе пользователя.

**OOD-цифра.** SWE-bench Verified 82.0 → 83.8 — это +1.8 pp, примерно 9 задач из 500. Прогон — «one attempt per instance» (`domains/coding/scripts/swe_eval.sh:15`). Непарная SE разности при p≈0.83, n=500 ≈ 2.4 pp (calc), так что +1.8 ≈ 0.75σ. Даже парное сравнение с одной попыткой не спасает от флипов агентных прогонов. Число сидов не указано ни для Table 1, ни для Table 2 (arxiv HTML v2, 2026-09-29).

**Релиз расходится со статьёй.** Issue #2 (`gh issue view 2 -R google-research/rrsi`, открыт 2026-09-25) фиксирует два расхождения:
- В релизе нет переключателей для абляций Table 2.
- `edit_budget` никогда не доходит до `b_min`: `budget_table(20,1,4)` = `[4]*8+[3]*5+[2]*7` (`rrsi/schedule.py`).

Автор подтвердил: «every reported run used a final-round budget of 2», флаги абляций будут «in the next commit». Состояние репозитория на 2026-09-29: 811 звёзд, 66 форков, 4 коммита, последний push 2026-09-23. Независимого воспроизведения нет, первое только собирается (Prithvi1994 в #2). Звёзды меряют бренд Google Research и дистрибуцию, а не проверку.

**Механизм удорожания виден в коде.** Cost rule меряет ΔC относительно **текущего incumbent** (`rrsi/evaluate.py:131-135`, `rrsi/selection.py` `cost_rule`). Внутри полосы шума новизна (`w_n = 0.5`, `w_c = 15`) пропускает +3.3% токенов при нулевом приросте (calc).

Сверху идут вызовы analyst, proposer и critic. При 1.56–2.42M токенов на триал workspace-прогон стоит порядка **15–24 млрд policy-токенов** (calc). Стоимость статья не публикует.

**Перенос на наши модели.** По их же README, с Gemini 3.5 Flash прирост на TB2.1 +14.1, с Opus 4.8 +6.0. Чем сильнее модель, тем меньше выигрыш от харнесса. VULYK работает на Opus 5.5 / Sonnet 5.5 / Fable 5.1 (`CLAUDE.md:35`), для них ожидаю меньше; это не измерено. Кроме того, их «харнесс» — один агент в терминальном цикле. Харнесс VULYK — это мульти-агентная оркестровка с владельцем в контуре.

## 2. Главная проблема переноса: у VULYK нет Evaluate()

RRSI держится на трёх вещах одновременно:
1. фиксированный, воспроизводимый набор задач (парное сравнение на тех же задачах, поэтому delta = 0.017);
2. дешёвый числовой вердикт (скрытые тесты);
3. замороженная policy в одном окне замера.

У VULYK нет ни одной из трёх.

**Данные.** Тут, в репозитории VULYK:
- `memory/stats/council.jsonl`: 16 строк, 5 спек за 11 дней.
- `ship.jsonl`: 7 строк.
- `human.jsonl`: 5 строк, все `ACCEPTED`, ноль `REJECTED`.

По всем ульям `docs/specs/token-audit/report.md:51-53` даёт 44 задачи за 13 дней. Каждая задача новая, в своём проекте, своего размера. Спарить не с чем.

**Шум по токенам.** Медиана 13.5M взвешенных, p75 27.6M (`token-audit/report.md:53`). Отсюда σ в логарифме ≈ ln(27.6/13.5)/0.674 ≈ 1.06 (calc). Чтобы увидеть −20% токенов при α=0.05 и мощности 0.8, нужно ≈ 2·(2.8)²·1.12/ln(0.8)² ≈ **350 задач на плечо** (calc). Это ~100 дней текущего потока всех ульев на одно плечо.

**Шум по вердиктам.** С первого раунда GREEN проходят 32% (`report.md:31`). Сдвиг 32% → 45% требует ≈ **216 спек на плечо** (calc). Любой «замеренный рост» за неделю или месяц окажется внутри полосы шума.

**Сигнал загрязнён инфраструктурой.**
- В `council.jsonl` есть ESCALATE с «haiku ABSENT» и «sonnet ABSENT» (строки 11, 13).
- В `human.jsonl:4-5` — ложные срабатывания taint.
- «56% прогонов драйвера останавливаются до вердикта» (`report.md:35`).
- `anomalies.jsonl`: 167 из 195 строк — `scope_breach`. В `scope.jsonl` у 127 из 140 историй `out_of_scope>0`. Детектор, который срабатывает на 91% историй, ничего не различает.

Если сделать PASS-rate целевой функцией, мы будем оптимизировать сантехнику, а не качество.

**Харнесс нестационарен.** С 0.12.0 по 0.20.0 прошло 9 минорных версий за 16 дней (`ship.jsonl`, git tags). Пол моделей сдвинулся 2026-09-28 (ADR-015). Понятия «тот же H₀ в том же окне» у нас нет.

**Цена одного Evaluate.** Возьмём 10 переигранных спек × k=2: это 20 прогонов × 13.5M взвешенных ≈ 270M на кандидата. Двадцать раундов × 2 кандидата дают ≈ 10.8 млрд взвешенных, то есть порядка $36k по медиане $45 за сессию (`report.md:19`, calc). Это против жалобы владельца на 3M токенов за задачу (`docs/specs/token-audit/brief.md:9`).

**Уже существующий пример шумового сигнала.** `/vulyk-evolve` печатает сигнал «escaped defects > REJECTED» на недельных счётчиках 0–2 (`.claude/commands/vulyk-evolve.md:42`). Решение по n=1 против n=0 — ровно то, что RRSI запрещает своим noise floor.

## 3. Противоречия с VULYK и опасные идеи

1. **Самоприменение.** RRSI сам делает fast-forward ветки (`rrsi/loop.py:327`). У VULYK: «Nothing self-applies» (`docs/self-evolution.md:16`), «Apply nothing to the main branch yourself» (`vulyk-evolve.md:59`). Автоматическое принятие ломает человеческий гейт — единственное, что сейчас держит `/vulyk-evolve` от переобучения.
2. **Goodhart на судье.** Главная причина RED — `lead-review` BLOCK, 39 из 64 (`report.md:30`). Оптимизатор с целью «меньше раундов» первым делом смягчит промпт ревьюера. Это оптимизатор, настраивающий судью по вердиктам судьи, то есть обход принципа «The family that builds never judges» (`CLAUDE.md:35`, ADR-015 §1). С целью «меньше токенов» оптимизатор выкинет проверки. С целью «больше PASS» будет подгонять под совет, а не под намерение владельца. Настоящий сигнал качества — override владельца, и у него n ≈ 5.
3. **Exploration на нетронутые компоненты.** При stall proposer обязан трогать `K_str = client_tool, skill, memory, subagent` (`rrsi/history.py:196-204`, `components.py`). Для VULYK это прямой путь к «делает слишком много»: ADR-008 (цитата владельца «очень долго делает несложные задачи») и ADR-013 Light VULYK шли в обратную сторону, к меньшему числу агентов.
4. **Храповик стоимости.** См. §1: даже регуляризованный RRSI вышел на +55% токенов к H₀. Law 2 («No overengineering») и `docs/token-economy.md` требуют обратного знака.
5. **Отдельная машина поиска.** Proposer, analyst, critic, digester, calibrate, worktree на кандидата — это новая подсистема ради сигнала, которого нет. Law 2, «no speculative abstractions».

## 4. Steelman: что выживает

Статья ставит честный диагноз, и он про нас. Нерегуляризованная эволюция переобучается и раздувает токены: в Table 2 у unregularized evolve +3.4, OOD +0.6 и 3.80M токенов на триал. Сегодняшний `/vulyk-evolve` по устройству и есть нерегуляризованный. Предложения строятся из списков трения, нет полосы шума, нет правила цены, нет памяти об отвергнутых гипотезах (grep по `previous|ledger|already tried|reject` в `vulyk-evolve.md` находит только счётчик REJECTED в `human.jsonl`). Его спасает только человеческий гейт. Три дешёвые вещи из RRSI не требуют Evaluate():

- **История правок с фальсифицированными гипотезами** (`rrsi/history.py`: одна JSONL-строка на правку — component, hypothesis, measured change, verdict; tried set, чтобы «a falsified hypothesis is not redrawn»). В VULYK это ответ на «не забывать контекст, чтобы он не разрастался». Одна строка на гипотезу, растёт с числом предложений, а не с числом сессий. Эволюция её читает и не переподаёт отвергнутое без новой улики.
- **Правило цены как вопрос ревью, а не формула.** Любое предложение эволюции, которое добавляет диспатч, агента или прозу в всегда загружаемый пакет, называет улику, которой оно оплачено. По умолчанию направление — удаление. Идёт от относительного H₀, а не от incumbent, чтобы не было храповика.
- **Честность шума.** Печатать n рядом с каждой недельной цифрой и не называть изменение улучшением по недельным счётчикам. Это исправляет существующий дефект `vulyk-evolve.md:42`.

Prune set уже есть: «unused for 3+ weeks → archive candidates» (`vulyk-evolve.md:57`). Worktree на кандидата уже есть в VULYK.

## Вердикт

| Идея RRSI | Итог | Причина |
|---|---|---|
| Автоматический цикл Evaluate → argmax над evolve set | **умирает** | нет воспроизводимого набора; ~$36k на прогон (calc); нужно 216–350 задач на плечо против 44 за 13 дней |
| Самоприменение победителя (fast-forward) | **умирает** | ломает человеческий гейт (`self-evolution.md:16`) |
| Целевая функция из PASS / rounds / tokens | **умирает** | Goodhart: смягчает `lead-review`, обходит «builds never judges»; сигнал загрязнён ABSENT и taint |
| Noise-adjusted floor (delta, calibrate) | **умирает как механизм, живёт как правило** | delta при нашем n не оценить; печатать n, не заявлять рост внутри шума |
| Cost rule beta0/beta1 | **живёт как вопрос ревью** | формула даёт храповик (+55% к H₀); вопрос «чем оплачено» дёшев и совпадает с Law 2 |
| Annealed edit budget | **умирает** | нет раундов; в релизе с ошибкой (#2); атрибуцию уже даёт ревьюируемый changeset |
| Edit history / tried set | **живёт** | дёшево, ограниченный размер, закрывает «помнить, не разрастаясь» |
| Stall → exploration на untried компоненты | **умирает** | толкает к новым subagent/memory/skill, против ADR-008/013 |
| Critic leakage screen | **умирает** | проверки ADR-014 специфичны по замыслу; `lead-review` уже читает diff |
| Prune set | **уже есть** | `vulyk-evolve.md:57` |
| Worktree на кандидата | **уже есть** | нейтрально |

**Выживший минимум.** Добавить в `/vulyk-evolve` журнал гипотез: одна строка на предложение (component, hypothesis, evidence, verdict владельца), читается перед следующим предложением, отвергнутое без новой улики не переподаётся. Плюс две строки в шаблон ревью: «чем оплачено добавленное (токены/диспатчи, относительно релиза, а не прошлой недели)» и «n рядом с каждой цифрой, без заявлений о росте внутри шума». Ни Evaluate(), ни автоматического отбора.
