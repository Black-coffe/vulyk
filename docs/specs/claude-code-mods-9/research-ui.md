## 1. Filetree

- Mechanism: a real mod (`hooks/hooks.json` -> `register.tsx`). Draws a **docked `Pane`** (`$.ui.open({id: PANE})`, `ui.render` on `Pane`). Needs fullscreen layout (`/tui fullscreen`) and a terminal >= 110 columns; Desktop app docks it itself (docs/sidebar.md).
- How it knows what Claude touches: **`tool.call` hooks** (register.tsx:3187 for Edit/Write/NotebookEdit/Bash/PowerShell; :3262 for Read; extra per-tool hooks at :3272). For Bash it parses the command text (regexes `WRITES`, `readOnly`, `gitActions`; work.ts) - so shell-borne reads/writes are heuristics, not guaranteed (docs/guards.md says so itself). Also `turn.start/complete`, `session.start/end`, `prompt.submit`, `ui.render` on `AssistantMessage` (turns `path:12` refs in replies into links). Not transcript, not an fs watch for Claude activity; fs watch (inotifywait, Linux only, optional) is only for live tree refresh.
- Model calls: **none** found (no `$.model.*`; `rg` for it empty). Extra processes: `git`, `grep`, optional `magick/ffmpeg/pdftoppm/soffice/pandoc/inotifywait` through `$.process`. So "spends no limits" is true as far as code shows; it does spend local CPU/process spawns.
- Writes on disk: guards via `$.store.set` (mod store, "under your Claude configuration, never in the repo"); marker temp files `$TMPDIR/filetree-<session>-N.mark`; a private 700 cache folder for previews (peek.ts); `/filetree keys` edits `~/.claude/keybindings.json` (keybind.ts, after asking). Active side effects: `/cd` into another repo ("Follow work", default on, `$.command.run({command:'cd'})`), and **guards that deny Edit/Write/NotebookEdit** (`tool.check` hook) - it can change Claude's behaviour, not only display.
- Platforms: terminal + Desktop app; README/docs: tested Linux, macOS, Windows (CI matrix ubuntu/macos/windows); Windows caveats: folder sizes via listings, treemap one level; no inotify live updates; no Desktop split preview; mods do not load in WSL sessions of Desktop. Pictures need Ghostty/kitty outside tmux. Not VS Code-specific (VS Code not mentioned for Filetree; the mods doc says Pane renders in VS Code ext >= 2.1.299 but Filetree does not claim it).
- Maturity: young (5 weeks, 183 commits, v0.8.0), very active, CI (lint, tsc, oxlint, contrast, platform matrix, zizmor), tests via `claude plugin test`. Docs good.
- Weaknesses/risks: 4.6k-line single file; Bash parsing heuristic; "Follow work" `/cd` moves your session by itself (can surprise); guards are advisory vs Bash (text match only); depends on a Claude Code version that is 2.1.306+.
- Collision with VULYK pulse: **none on render sites** - Filetree draws `Pane`, `AssistantMessage`; pulse draws `Spinner`, `AbovePrompt`, `TurnDuration`. Both hook `tool.call`/`turn.*`/`session.*` but as pass-through middleware. Only competition: horizontal space (pane needs >= 110 cols; pulse is a row) and one more `tool.call` interceptor in the chain (Filetree's Edit/Write hook awaits `next` and does git work around it - small latency, no semantic conflict).

## 2. Terminal Browser

- Mechanism: **primarily a standalone terminal app** (`terminal-browser` CLI), not a mod. The Claude Code piece (`claude-code-plugin/`, plugin v0.0.2) is a thin mod that: registers `/browser` + optional agent tools `mcp__terminal-browser__open/close` (off by default, `agentTool` userConfig), opens a **`Pane`** (`$.ui.open`, `rows: 24`) and **blits frames** into it with `$.ui.blit` as an `Image`, polling a local bridge.
- What it embeds: a **real Chromium via Electron offscreen rendering** (README "How does it work?"; `pixel/packages/pixel/src/web/offscreen.ts`, `host.ts`). Pixels go to the terminal through the **kitty graphics protocol** (+ unicode placeholders for the plugin). A separate Electron/Chromium process (daemon, `browser/src/daemon.ts`); a separate Node "claude-bridge" process (`cli/src/claude-bridge.ts`) serves HTTP on `127.0.0.1:<random port>` with a random 24-byte token (`crypto.randomBytes(24)`), passed by env `TERMINAL_BROWSER_AGENT_TOKEN`. Input is synthesised from terminal mouse/keyboard events; on macOS a background Swift app reads OS input events.
- Model calls: none in the plugin. But a **CLI `action` command is "agent-browser compatible"** and the optional tools let the agent drive the page - the agent then reads page content into its context (token cost = what the agent fetches). Also "ctrl+g" element selection and recording send page context to the agent on user action.
- Writes on disk: browser profile/cookies (Electron sessions, partitions `persist:`), `~/.local/state/terminal-browser-*/logs/` (incl. `telemetry.jsonl`), the bridge launch log. **Telemetry**: pseudo-anonymous usage + crash reports on by default; off with `DO_NOT_TRACK=1`, `TERMINAL_BROWSER_NO_TELEMETRY=1` or config.
- Install: `curl -fsSL https://terminal-browser.sh/install | bash` or `brew` - downloads a prebuilt Electron app + binaries (release workflow in repo; I did not audit the binaries). Plugin needs the user to set `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` in README - **but the official mods docs say Claude Code v2.1.287+ ignores that variable** (stale README step).
- Platforms: macOS and Linux; **Windows only via WSL** and few kitty-graphics terminals (README names noctty.com). Plugin requires a kitty-graphics + unicode-placeholder terminal (Ghostty, kitty, cmux, supacode); other terminals "may garble the TUI"; multiplexers break it (tmux not yet through the plugin; herdr slow). Native Windows Claude Code, Windows Terminal, VS Code integrated terminal for the plugin path: not supported / unverified. Desktop app / VS Code chat panel: no (`Image` is terminal-only per official elements table).
- "Experimental": the Claude plugin README opens with "This plugin is experimental and does have some known limitations"; caveats: mouse position slightly off, OS "local network" prompt for the localhost bridge, high min width of chat area, depends on the unstable function-hooks API. The standalone browser is not labelled experimental.
- Security: Electron webContents use `sandbox: true, nodeIntegration: false, contextIsolation: true` (host.ts:64-68; devtools.ts:66-68) - so a page does not get Node. Permission prompts exist (camera/mic etc. need an in-terminal prompt; geolocation and display-capture are never granted; `permissions.ts`). The bridge is localhost + token. Residual risks: it is a full Chromium on your machine (browser CVEs, update lag - self-updating via `terminal-browser upgrade`), `nodeIntegrationInSubFrames: true` is set (harmless with sandbox but unusual), `--ssh` mode proxies all page traffic through a remote host, the agent-control CLI lets the model act in logged-in sessions (prompt-injection from page content to agent), telemetry on by default, arbitrary `curl | bash` install. Untrusted pages run in a sandboxed renderer, not with local file access by design; I did not test escapes.
- Maturity: 4460 stars, 126 open issues, releases v0.15.3 (2026-10-30), pixel-v0.2.10; plugin v0.0.2 = weakest part.
- Collision with VULYK pulse: **none on render sites** (it uses `Pane` + `Image` blit). Costs: the pane eats width the band/spinner row would not need anyway; the bridge polling adds `$.http.fetch` traffic; if kitty graphics is unsupported it can corrupt the whole TUI including pulse's row.

## 3. Claude Skins

- Mechanism: a large redraw mod. `ui.render` hooks on **`ToolUse`, `ToolGroup`, `ToolResult`, `UserMessage`, `AssistantMessage`, `CommandOutput`, `Spinner`, `TurnDuration`, `AbovePrompt`, `AskUserQuestion`**, plus `Pane` for settings/gallery (register.tsx:907-1311). Also `prompt.compose` (injects a ~130-token "mermaid fences draw here" hint, not in `claude -p`; `/skin hints off` removes it), `session.append/measure`, `turn.*`, `tool.call` (timings, files touched) and a `design` tool (`mcp__skins__design`) so Claude can build a skin.
- Is it "themes and icons"? Partly. It does 16 colour skins (noir, tokyo-night, dracula... repaint any colour) and icons on the **desktop** only (terminal draws no `Svg`; terminal gets a rail), but it also redraws tool rows, diffs (desktop), tables, code highlighting, Mermaid in 17 chart kinds, math, shell cards, links, folding, a **usage band above the prompt** (context + plan-limit meters, Compact button with nudge at 70%), **spinner words with shimmer** and the **turn footer words**. README: "Only the drawing changes: the stored conversation and what the model reads are untouched" - except the hint section and the design tool.
- Model calls: none (`rg $.model` empty). Token cost: ~130 tokens of system-prompt section per session (README says estimated) + the `design` tool schema; Compact button runs Claude's own `/compact` only on press.
- Writes on disk: settings in the mod store; no file writes found beyond store. Network: one daily GET of the repo's `plugin.json` on raw.githubusercontent.com (README Privacy). Runs `defaults`/`gsettings` for light/dark on `auto`. Reads `$.session.usage` (context + rate limits).
- Platforms: terminal and Desktop Code tab; Windows verified by hand at 0.3.0 (terminal and desktop), CI on Linux/Windows/macOS from 0.5.0; VS Code and mobile untested; macOS never looked at by hand (docs/compat.md).
- Maturity: 5 weeks old, 263 stars, 50 commits, 0.5.16, tests (168 engine tests), benchmark: tool-row mount median 4.5 ms (0.4.0: 1.4 ms) - perf regressing release over release but small. Author maintains a marketplace "hellosverre-mods" with `mod-store` claiming ~2,700 mods (claim from README, not checked).
- Weaknesses: scope creep; many parts are off-by-default or partial; fallbacks to native drawing in many cases (README "Known limitations" table); desktop vs terminal differences; own README comparison names competitors (Prismantis, glint, tweakcc) - overlap is a crowded niche.
- **Collision with VULYK pulse: YES, direct.** Skins hooks exactly pulse's three render sites: `Spinner` (words + shimmer), `AbovePrompt` (usage band), `TurnDuration` (footer words). Both are middleware chains.

## Conflict resolution between mods (official docs, fetched 2026-11-05)

- Hooks on the same event/render site form **one middleware chain**; `next(e)` calls the following mod or Claude Code. "The first mod is outermost: it sees the event before the others and the result after them, and it decides whether the others run at all. A later mod can't stop an earlier one from seeing an event." (events.md, "The order mods run in".)
- Order by origin: built-in guard + org `prependPlugins`; then **mods you install**; then org `appendPlugins`; then other built-in mods. "Within one module, hooks run in the order `register` called `on`." Among user-installed mods the doc gives no explicit order beyond "a mod runs before the mods it lists under `dependencies`" - so between pulse and Skins (both user-installed) the order is **not specified by the docs** (I did not find a stated rule: unverified).
- Practical effect on one `ui.render` site: the outer mod either calls `next` (and then the inner mod's tree is what it receives, which it may wrap or discard) or answers itself (inner mod never runs). Skins' Spinner hook, if inner, sees pulse's tree only through its own `next` and **replaces** it (it returns `spinnerRow(...)`, not a wrapped `next` result, unless `active===null`/`calm`/`shimmer` off/`message!==null`); `TurnDuration` likewise returns `footerRow(...)` without `next`. So whoever is outer wins the Spinner and the footer; the inner one is silently dead. `AbovePrompt` in Skins is nicer: it renders `<Box>{usageBand}{theirs}</Box>` with `theirs = await next(e)` and yields to `e.props.hasSurvey` ("Another mod's drawing there, and a survey, keep their place") - so band stacking works if pulse is inside, and pulse's own note says Claude's "You should know" note wins its band.
- Surfaces a mod can draw (reference.md, Render sites): `Pane` (terminal/desktop/VS Code), `AbovePrompt` (band; terminal/desktop), `UserMessage`, `AssistantMessage`, `ToolUse/ToolResult/ToolGroup`, `CommandOutput`, `AskUserQuestion`, `ToolProgress` (terminal), `Spinner`, `TurnDuration` (terminal only), `InfoNotice` (terminal), `SessionMode`, `PromptHint`; plus `$.ui.toast/notify/status/log/notice/ask`. **There is no theme render site**: "themes" are mods recolouring what their hooks draw (Skins recolours only what its hooks redraw; "Recolours Claude Code's own UI: No" per its own comparison table; tweakcc patches the binary). Permission prompt cannot be restyled by mods. Status line is a separate non-mod feature (settings status line command).
- Docs mention the VS Code panel draws `Pane`, `Spinner`, messages but not `AbovePrompt`/`TurnDuration`.

## Verdict on collision with VULYK pulse (`.claude/mods/vulyk-pulse`, docs/pulse.md)

Pulse hooks `ui.render` on `Spinner`, `AbovePrompt`, `TurnDuration` (register.tsx:243/251/264), hive-only, terminal-only, never calls the model.

- Filetree: no collision. Compatible; only screen width and an extra `tool.call` hop.
- Terminal Browser: no collision on sites; compatible when the terminal supports kitty graphics; risk of TUI corruption otherwise; the heaviest dependency (Electron) and the weakest plugin.
- Skins: **collides on all three of pulse's sites**. With both enabled, the outer mod's Spinner/TurnDuration replaces the other's (Skins returns its own rows without wrapping `next`), so pulse's agent dots, wave and token figure, or the "N agents · ≈X tok" closing line, can vanish silently; the band stacks (Skins puts its usage band above whatever `next` returns, if pulse is inner). Which one is outer is not specified in the docs for two user-installed mods. Mitigations to note, not to build here: `/skin shimmer off` + `/skin words claude` + `/skin band off` leave Skins' spinner/band alone (Spinner then calls `next` with only the word changed when `shimmer` off; TurnDuration still goes to `footerRow` unless `/skin off` or `calm`, so footer cannot be handed back by a part toggle - from code, not tested).
